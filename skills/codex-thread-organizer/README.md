# codex-thread-organizer

> Codex 会话标题、收口摘要和回溯索引维护。**适用范围标注**：个人工作流。

## 是什么

`codex-thread-organizer` 用于维护 Codex 会话的可回溯性：给线程生成稳定、可检索的标题，整理连续主线编号，在收口时更新生命周期阶段，并生成必要的摘要、交接包、索引和归档建议。

标题回答的问题是：`这个会话最终值得因为什么被找回来？`

它解决个人会话导航问题，不处理代码实现、项目文档治理或仓库知识沉淀。

## 主要规则

- **对象优先**：有持续演进对象时使用 `[web-ai-daily-paper] 设计收敛`；跨对象治理才使用 `[Skills] 发布流程统一`。
- **生命周期**：区分初始、当前和收口标题。只有明确任务转向才更新当前标题，收口时根据实际产物和稳定终态重算。
- **可读不等于合格**：还要检查对象前缀、真实阶段、重复入口和连续主线；`搭建`、`升级`、`完善` 等动作不能掩盖实际仍处于评估或设计的状态。
- **全局聚类后再跳过**：先按对象、cwd、版本、交接、共享产物和重复首轮目标寻找候选家族，再判断单个标题是否可以保留。
- **家族必须闭合**：发现同对象主线后，需要对范围内全部成员给出关联和编号结论；不能只处理标题最差的一条，也不能因某条标题已经清晰就把它排除在编号预览外。
- **生命周期动词强制复核**：`设计`、`升级`、`搭建`、`推进`、`完善`、`重构` 等标题遇到持续更新、版本发布或交接信号时必须复核真实终态。
- **证据按时间倒序解释**：线程工具返回最近轮次优先；较新的实现、实测、合并和发布结果覆盖首轮 preview 与早期设计状态，旧轮次只用于确认来源和交接。
- **耐久任务与最后交互分离**：实现、MR、版本和发布属于线程的耐久结果；后续发送状态、组织交接或记录改进，不会把主线重新分类成 sidecar。
- **轻量取证**：先用 `title + preview + cwd` 判断；只有低信息、标题漂移、关系或编号不清等异常项才补读最近 2–3 个关键轮次。
- **上下文限流**：补读始终使用 `includeOutputs=false`，不读取命令输出，不把原始响应或完整正文复制到工作记录；每个异常项只保留 500–1000 字符证据卡。
- **拆分判断**：主题、类别、关联、编号分别给置信度。任一标题关键判断不稳定，就进入 `needs-review`。
- **安全应用**：`确认应用` 和 `都改掉` 都只应用确定项；Automation、系统线程和不确定项默认跳过。
- **编号边界**：编号序列以“对象/类别 + 项目或工作上下文”为边界。批量扫描可给关系明确的未编号主线从 `01` 建序列，单会话不会凭一个候选创建编号家族。

## 命令

| 命令 | 用途 |
| --- | --- |
| `codex-thread-organizer:init` | 初始化当前会话为常驻线程命名管理器，不自动扫描 |
| `scan` / `codex-thread-organizer:scan` | 默认扫描最近 10 个可见线程，只预览异常项 |
| `scan all` | 分批扫描宿主可见范围内的全部线程 |
| `audit 5` | 抽样补读 5 个线程，评估标题准确度和误判模式 |
| `renumber <对象或类别>` | 只预览指定主线的关联与重编号方案 |
| `codex-thread-organizer:rename` | 只处理当前或指定线程重命名 |
| `codex-thread-organizer:handoff` | 只生成下一会话交接包 |
| `codex-thread-organizer:closeout` | 组合执行收口命名、五行摘要和必要交接 |
| `确认应用` | 应用上次预览中的高置信 `rename` 项 |
| `都改掉` | 应用全部确定的 `rename` 项，仍跳过 `needs-review` |

`scan` 会主动报告元数据范围、补读数量、未读范围、Automation/系统跳过数量和 `needs-review` 的停止原因，避免把轻量扫描误解为全量正文审阅。

异常较多时允许补读多个线程。成本控制依赖每个线程只读最近 2–3 个关键轮次，而不是人为压低补读总数；判断编号时必须补读足以覆盖整个候选家族的成员。

输出前还会检查：所有候选家族是否完整处置、所有重复索引是否区分范围、所有 `rename` 是否为四项高置信，以及建议前缀是否错误重复当前 cwd/project。

范围、补读、元数据跳过、Automation 保护和动作数量必须能完整对账；项目目录名与对象相同时，编号家族优先使用既有短对象名，不机械复制 cwd 全名。

同对象、同工作上下文出现多个主线成员时，只允许三种结论：完整编号序列、证据充分的独立角色，或 `needs-review`。不允许一条改名、一条跳过却不给家族关系结论。

扫描严格按“列出范围 → 对象归一化 → 个体异常 → 家族聚类 → 限量补读 → 个体与家族联合决策 → 闭合检查 → 输出”执行。若最近 3 轮明确指向缺失的收口或交接证据，最多再补一页 3 轮；仍不清楚就停止在 `needs-review`。

## 验收方式

语义标题不存在唯一标准答案，固定标题断言容易把 Skill 调成只适配夹具。当前以真实前向测试为主要验收方式：

- 新建无历史答案的独立 Codex 会话；
- 使用 `gpt-5.6-luna`、`medium` 执行真实 `scan`；
- 不向执行会话泄露预期标题、已知缺陷或修正规则；
- 在独立验收会话人工检查漏检、误报、生命周期、关系、编号和 `needs-review` 边界；
- 保留格式、安装发现、工具安全边界等确定性检查，但不把精确标题命中率当作总体质量证明。

2026-07-16 的最终用户验收使用全局安装副本、`gpt-5.6-luna`、`medium` 扫描最近 20 个真实线程：限量补读 14 个异常或关系候选，预览 9 条高置信重命名；用户确认后 9 条全部应用并核验成功，0 失败，Automation/system 与归档候选均未被误操作。该结果证明本次真实样本通过，不代表已建立总体准确率统计结论。

## 前置条件与降级

- 宿主提供 thread tools 时，可以列出、限量读取和重命名线程。
- CLI 或其他宿主没有重命名工具时，只输出建议标题、收口信息和缺失证据。
- 线程工具失败时不会直接写本地 Codex 数据库；连续主线编号缺少关联证据时保持临时无编号标题或进入 `needs-review`。
- 分派或新建线程只使用明确的目标 `threadId`；`source_thread_id` 仅作为来源证据。
- 正常运行不依赖 subagent，规则和取证预算按 `gpt-5.6-luna`、`medium` 的低成本运行目标设计；实际模型由宿主配置决定。
