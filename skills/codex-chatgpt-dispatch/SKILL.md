# Codex ChatGPT Dispatch

把 Codex 当前掌握的真实工作现场压缩成可审查的 `handoff.txt`，通过内置 Browser
交给用户指定的 ChatGPT 网页档位完成一次高质量判断，再由 Codex 回到本地证据完成
核验和后续工作。

第一版只支持显式触发，保持 instruction-first。它是轻量调度协议，不是模型网关、
账号管理器、任务队列或无人值守自动化。

## 先确定本次动作

从用户原话判断动作范围：

| 用户表达 | 动作 |
| --- | --- |
| “先整理 handoff”“不要提交”“整理好给我看” | 只准备材料，完成后停止 |
| “准备后让我确认” | 准备并展示提交摘要，等待确认 |
| “用 `<目标档位>` 提交”“整理后直接发送” | 完成质量门后可以提交一次 |
| “拿新增证据在原会话继续讨论”“回复原来的 Pro 再审一轮” | 复用原网页对话，准备续评 handoff，获得本次发送授权后提交一次 |
| “处理这个”或目标、对话、授权不清 | 先准备材料，再集中确认缺失决定 |

显式触发只授权加载 Skill 和准备上下文，不自动授权发送。调度授权也不扩大当前任务
已有的本地读写、Git、发布或其他外发权限。

确认当前执行表面：

- 只准备 handoff 时，不要求 Browser 可用。
- 真正提交要求 ChatGPT 桌面中的 Codex 和内置 Browser 当前可用。
- 内置 Browser 不可用时停止在提交前，不切换到 Quick Chat 原生调度、API、MCP、
  代理、私有接口、其他账号或另一条网页链。
- 用户手工接管只算降级恢复，不算本次自动调度成功。
- 每次运行读取当前页面状态，不把某次工具名、DOM、模型列表或内部 thread 字段当作
  永久契约。

## 1. 盘点必要上下文

只读取足以让目标模型独立完成本次判断的材料：

- 当前任务的真实目标、预期交付和成功标准；
- 用户已经确认的约束、偏好和非目标；
- 相关代码、文档、设计、Git diff、测试和运行证据；
- 当前方案、主要分歧和可能反例；
- 外部模型已经给过意见时，记录其上一轮结论、关键依据和当前不同意见；
- 首轮之后新增的用户决定、本地事实、实验结果和实现变化；
- 会实质改变结论的未知项；
- 外部模型需要直接读取的最少附件。

不要机械复制完整会话、整个仓库、无关历史或大段重复材料。信息不足会影响核心判断
时，先收集可在本地确认的事实；仍缺少用户决定时集中询问一次。

代码和仓库任务按相关性记录：

- 仓库与工作目录；
- 当前 branch 和 commit SHA；
- 工作区是否 dirty；
- 与问题直接相关的 diff；
- 已运行的关键测试、命令和结果；
- 每个附件被选择的原因。

本地路径只用于 Codex 定位材料，不能替代给网页端的上下文。目标模型不能访问某个
本地文件或目录时，必须在以下方式中选择一种：

- 作为已索引附件上传；
- 把决定结论的内容、结构、diff 或验证结果提取进 handoff；
- 只把文件名、仓库、branch 和 SHA 作为证据身份，同时提供必要事实摘要。

不要在 handoff 中仅写“请读取 `/Users/...`”或“详见本地仓库”。

## 2. 生成 `handoff.txt`

已有 case 或 artifacts 目录时，把文件放入对应运行材料目录。没有合适位置时使用安全
的临时目录，并返回绝对路径。至少保留到结果回收和本地核验完成。

按任务需要删掉空章节，但保留事实、推断、偏好和未知项的边界：

```text
任务目标
预期交付
已确认事实
当前推断
当前方案或实现
约束与非目标
判断标准
关键证据与附件索引
已知分歧
未知项
希望重点判断的问题
输出要求
```

让 handoff 满足以下质量：

- 信息足够支撑独立判断，不用追溯完整 Codex 会话；
- 明确允许目标模型反对当前方案并提出更优路径；
- 附件逐个说明用途、来源和可信边界；
- 代码结论绑定到真实 branch、SHA、dirty 状态、相关 diff 和验证结果；
- 网页端无法访问的本地路径已经转成附件、必要摘录或结构化证据；
- 不为追求短而删除会影响结论的条件；
- 不把推断、用户偏好或未经验证内容写成事实。

`handoff.txt` 是默认主上下文。ChatGPT 输入框只写简短控制语，例如：

```text
请完整阅读 handoff.txt 和已索引附件，基于其中的事实、约束与判断标准独立完成任务。
可以反对当前方案；请明确区分事实、推断、建议和待验证项。
```

角色、视角和输出格式按本次任务写入 handoff，不建立固定的
review / plan / implement 路由表。

### 同一任务续评

已经取得上一轮结果，又要携带新增证据复审时，默认复用原网页对话并生成
`handoff-followup.txt`。它不复制完整首轮 handoff，而是建立足够明确的证据桥：

```text
原始问题与当前目标
上一轮结论及关键依据
上一轮之后新增的用户决定
新增本地事实、实验或实现结果
哪些旧假设已被证实、限定或推翻
当前仍有分歧的决策点
希望重新判断的问题
要求说明维持、修订或反转结论的理由
第一版必须做、只保留规则、以后触发再做的边界
```

续评材料必须自包含到足以理解新增证据，不能只写“请结合之前内容重新看”。同时利用
原会话保留上一轮论证，不把所有历史再次上传。独立新问题或用户明确要求 clean-room
时才新建对话。

续评控制语应直接说明新证据和重审要求，例如：

```text
请结合原会话和 handoff-followup.txt 中的新增证据重新判断。不要以维持上一轮结论为
目标；请说明这些证据是否足以让你维持、修订或反转观点，并给出理由与最小落地边界。
```

## 3. 选择最少附件并检查外发风险

只附加用户明确选择或本轮 `handoff.txt` / `handoff-followup.txt` 明确索引、且与任务
直接相关的文件。

- 逐个核对文件名、数量和选择理由。
- PDF、DOCX、PPT 中的重要图表、流程图或设计图应单独作为图片附件；不要假设内嵌
  视觉信息会被完整读取。
- 上传失败且尚未发送时，可以修正或减少附件；持续失败则停止。
- 不调用私有上传接口，也不把用户手工上传记录为自动调度成功。

提交前直接阻止凭据、Token、私钥、Cookie、session dump、数据库备份、生产用户
数据、患者隐私或明显客户敏感材料。公司源码、业务日志、个人数据等能否进入当前
ChatGPT 账号取决于组织政策和用户外发授权；存在实质不确定性时停止确认。

不要读取、检查或持久化账号凭据、Cookie、Browser Profile 或认证存储。需要登录、
切换账号或确认身份时交给用户。

## 4. 通过提交前质量门

在任何 Browser 发送动作前重新检查：

- 目标、预期产物、判断标准和关键问题是否明确；
- 必要事实、证据、约束、分歧和未知项是否齐全；
- 相关本地文件是否在 handoff 生成后发生变化；
- 网页端不可达的本地路径是否已经转换为真实附件或可消费证据；
- 附件是否最少、已索引、无确定性高风险材料；
- 本次对话应新建还是复用；
- 复用对话时是否确认页面里存在上一轮问题和回复；
- 用户是否已经授权本次发送；
- 当前 Browser 是否连接到唯一、状态明确的 ChatGPT 页面；
- 当前网页账号是否符合用户预期；
- 页面实际选中的模型或推理预设是否与用户要求完全一致；
- 页面显示的附件名和数量是否与 handoff 索引一致；
- 同一请求是否已经在目标对话中提交。

对话选择规则：

- 独立任务默认新建普通 ChatGPT 网页对话，减少旧上下文污染。
- 同一任务的续评、追问或补充材料默认复用原网页对话。
- 续评默认只提交新增证据桥，不重复上传完整旧材料；旧材料已经失效时明确标记替代关系。
- 无法可靠判断是否同一任务时，给出一句建议并让用户决定。
- 每次追问都是新的发送，需要新的授权。
- Temporary Chat 只在用户明确需要 clean-room、理解 Memory 和恢复差异后使用。

模型选择规则：

- 只使用用户指定、提交时页面实际可选的模型或推理预设。
- 用户未指定时可以给一句成本与质量建议，但不能静默决定高成本档位。
- 目标不可用时停止，展示实际选项；不要选择近似档位。
- 不维护固定模型枚举，也不假设模型和推理强度可以任意组合。
- 页面显示 `Pro` 等产品档位时按页面原文记录，不根据标签猜测底层 GPT 版本。

展示紧凑摘要：

```text
目标：<一句话>
模型：<页面实际选项>
对话：<新建或复用>
材料：<handoff.txt / handoff-followup.txt> + <N> 个附件
风险：<无明显风险 / 需用户确认>
动作：<仅准备 / 等待确认 / 将提交一次>
```

只准备时在这里停止。已有清晰发送授权且质量门通过时，不重复索要形式化确认。
页面动作在执行时要求确认的，遵循当前产品的 action-time confirmation。

## 5. 通过内置 Browser 只提交一次

实际操作 Browser 前，加载当前会话提供的 `browser:control-in-app-browser` Skill，
完整遵循它的页面观察、唯一定位、文件上传、动作确认和状态核对规则。该 Skill
不可用时 fail closed。

调度期间优先保持 Browser 侧栏可见，方便用户观察过程和必要时介入。侧栏显隐只影响
可观察性，不作为执行或成功判据；如果当前产品无法控制侧栏显隐，但同一个 in-app
Browser 标签页仍可正常操作，则继续使用原有 Browser 链路，不因此阻断调度。

Browser 是第一版正常全链路适配器，按顺序完成：

1. 打开或接管用户可见的普通 `chatgpt.com` 页面。
2. 按对话选择规则新建或复用普通网页对话；续评时先确认上一轮上下文确实存在。
3. 观察并核对当前网页账号；需要登录或切换时交给用户。
4. 读取提交时页面实际存在的模型或推理预设，精确选择用户指定档位。
5. 上传本轮 handoff 文件和已索引的最少附件，核对附件名和数量。
6. 输入简短控制语。
7. 再次检查同一请求尚未发送、目标档位和附件仍正确。
8. 只执行一次发送动作，并确认页面已经接受该次提交。

Browser 只操作普通 ChatGPT 网页，不调用 API、MCP、代理、私有接口或其他账号。
页面是否已发送不明确时先只读检查同一对话，绝不再次发送。

## 6. 在同一网页对话中无干预等待

发送是本流程唯一不可重复的提交点。发送后保持同一 ChatGPT 网页对话，Browser
只进行不会改变本轮状态的等待和只读观察：

- 不点击“立即回答”；
- 不点击“停止回答”；
- 不因本地超时再次发送；
- 不复制请求并新开替代对话；
- 不静默切换模型或推理档位；
- 不因完成状态不清重试；
- 不在没有新授权时追问。

十几分钟或更长的推理可能是正常路径。长时间没有最终结果时，报告仍在等待并继续
观察同一网页对话。用户要求取消时，先说明可能损失当前推理，再按新的明确授权处理。

## 7. 由 Browser 读取同一网页对话结果

页面显示最终回复后，Browser 从本轮一直保持的同一网页对话读取完整结果并带回
Codex。正常路径不调用 `list_threads` 重新匹配候选，也不把 DOM 读取交给用户。

读取时核对：

- 最终回复属于本轮已发送请求；
- 回复已经完整结束，不把中间状态当作最终结果；
- 必要的代码块、表格、引用和结论已完整取得；
- 原网页对话仍被保留，便于异常恢复。

## 8. 只在 Browser 失败后恢复结果

只有 Browser 控制断开、页面不可恢复或结果读取不完整时，才进入原生 thread
恢复：

1. 使用当前可用的 ChatGPT 对话列表能力定位同一对话。
2. 使用读取能力取得完整回复。
3. 候选不唯一时停止确认，不按标题、时间或内部 ID 猜测。
4. 原生恢复仍失败时保留原网页对话和产品入口，由用户可见地复制或保存结果。

不要依赖固定 backing kind、thread ID 与网页 chat ID 映射，或所有网页对话都可见。
`send_message_to_thread` 不用于第一版提交或追问，因为它不能核对或覆盖 ChatGPT
页面实际档位。任何恢复失败都不得触发重新发送。

## 9. 完成本地核验

外部回答只提供高质量判断或候选产物，Codex 保留最终核验责任：

- 对照原始 handoff 检查目标、约束和关键问题是否覆盖；
- 回到仓库核对文件、Git 状态和实现事实；
- 对代码、命令或配置运行适度测试；
- 区分回答中的事实、推断、建议和待验证项；
- 续评时比较前后结论，记录模型维持、修订或反转观点的依据；
- 明确采纳、部分采纳、拒绝和待验证内容；
- 只在当前任务已有相应修改授权时继续实施。

交付时至少说明：

```text
目标档位：<页面实际选项>
对话：<可用的原网页对话引用>
handoff：<绝对路径>
回收方式：<Browser 同页读取 / 原生异常恢复 / 用户可见恢复>
调度状态：<自动调度成功 / 降级恢复 / 未提交>
核验结论：<已通过 / 部分通过 / 未通过>
采用情况：<采纳、部分采纳、拒绝、待验证>
结论变化：<首次审查 / 维持 / 修订 / 反转，以及主要依据>
```

默认不创建 response、validation、manifest、数据库或状态文件。只有任务价值和后续
复用明确需要时，才在已有 case / artifacts 中保存额外结果。

## 10. 技术方案审查的证据闭环

外部模型的第一轮结论与当前方案冲突时，先判断分歧属于哪一类：

- 用户目标或可接受代价：停止并由用户决定；
- 本地源码、构建、运行时或部署事实：回到本地核验；
- 可通过小规模对照验证的工程假设：在当前授权内设计受控 Spike；需要新增写入或扩大
  实验范围时先获得授权；
- 纯设计判断：列出双方依赖的假设和重新评估条件。

只有新增信息可能改变判断时，才建议再次使用高成本档位。第二轮续评应提供控制变量、
代表样本、关键实现、自动检查、真实路径观测、工程成本和剩余未知项，并明确要求目标
模型说明新证据是否足以改变观点。

不要用多个模型投票替代事实，也不要在没有新增证据时连续追问。选型结论收敛后，再
单独要求区分：第一版必须建设、当前只需规则约束、真实信号出现后再建设。Codex 最终
把外部意见与本地证据合并为采纳、调整、拒绝和待验证清单。

## 失败处理

| 场景 | 处理 |
| --- | --- |
| Browser 或 Browser Skill 不可用 | 停止在提交前，不切换执行链 |
| ChatGPT 网页未登录或账号不符 | 停止，交给用户登录、切换或确认 |
| 目标档位不可用 | 不提交，不自动选择近似档位 |
| 附件持续上传失败且未发送 | 停止；手工接管只算降级恢复 |
| 页面目标、附件或发送状态不唯一 | 停止确认，不猜测、不再次发送 |
| 页面已发送但仍在推理 | 同页被动等待，不干预 |
| Browser 控制断开或读取不完整 | 恢复同一页面，失败后才尝试原生 thread 读取 |
| 原生恢复候选不唯一 | 停止确认，保留原对话和产品入口 |
| 输出质量不足 | 先本地分析；追问或重开需要新授权 |
| 续评材料只有本地路径或“同上” | 停止提交，转换为附件、必要摘录和新增证据桥 |
