# Codex ChatGPT Dispatch

整理 Codex 当前掌握的必要现场，通过内置 Browser 交给用户指定的 ChatGPT 网页
档位完成一次高质量判断或图片生成，再由 Codex 回到本地完成核验和后续工作。默认先
判断一条文本输入能否完整承接必要上下文；能承接时直接输入，不创建 handoff 文件。
只有信息需要结构化拆分、较多附件索引、跨轮复用，或用户明确要求时，才生成任务化 handoff。
附件任务独立判断当前上传路径；内置 Browser 不支持自动上传时，使用一次人工上传
检查点。无附件时仍可走完整自动链。

第一版只支持显式触发，保持 instruction-first。它是轻量调度协议，不是模型网关、
账号管理器、任务队列或无人值守自动化。

## 先确定本次动作

从用户原话判断动作范围：

| 用户表达 | 动作 |
| --- | --- |
| “先整理 handoff”“不要提交”“整理好给我看” | 只准备材料，完成后停止 |
| “准备后让我确认” | 准备并展示提交摘要，等待确认 |
| “用 `<目标档位>` 提交”“整理后直接发送” | 完成质量门后可以提交一次 |
| “组织发送就行，不用等结果” | 提交一次，确认页面接受后立即返回 |
| “材料整理好，我来上传” | 准备上传卡，把页面停在可上传状态并等待用户 |
| “生成一张图片并保存到本地” | 按复杂度准备提示词或 handoff，提交一次并回收图片产物 |
| “拿新增证据在原会话继续讨论”“回复原来的 Pro 再审一轮” | 复用原网页对话，准备最小续评材料，获得本次发送授权后提交一次 |
| “完整留存这次对话” | 结果完整后生成一份耐久的可追溯记录 |
| “处理这个”或目标、对话、授权不清 | 先准备材料，再集中确认缺失决定 |

显式触发只授权加载 Skill 和准备上下文，不自动授权发送。调度授权也不扩大当前任务
已有的本地读写、Git、发布或其他外发权限。

确认当前执行表面：

- 只准备提交材料时，不要求 Browser 可用。
- 真正提交要求 ChatGPT 桌面中的 Codex 和内置 Browser 当前可用。
- 有附件时读取 [IAB 人工上传与排障](references/iab-manual-upload.md)；它是上传能力、
  冻结集合、人工检查点和异常恢复的唯一详细规则。
- 内置 Browser 不可用时停止在提交前，不切换到 Quick Chat 原生调度、API、MCP、
  代理、私有接口、其他账号或另一条网页链。
- 用户只完成人工上传、其余主链由 Browser 完成时，记录为“人工辅助调度成功”，
  不冒充“自动调度成功”；意外接管其他核心步骤仍算降级恢复。
- 每次运行读取当前页面状态，不把某次工具名、DOM、模型列表或内部 thread 字段当作
  永久契约。

### 附件能力边界

本轮包含附件时，完整读取 [IAB 人工上传与排障](references/iab-manual-upload.md)，
按其当前基线做一次只读预检。没有恢复信号时直接使用人工上传；真实能力探测
需要单独授权，且不使用项目材料、不发送消息。

## 1. 盘点必要上下文

只读取足以让目标模型独立完成本次判断的材料：

- 当前任务的真实目标、预期交付和成功标准；
- 用户已经确认的约束、偏好和非目标；
- 相关代码、文档、设计、Git diff、测试和运行证据；
- 当前方案、主要分歧和可能反例；
- 外部模型已经给过意见时，记录其上一轮结论、关键依据和当前不同意见；
- 首轮之后新增的用户决定、本地事实、实验结果和实现变化；
- 会实质改变结论的未知项；
- 外部模型需要直接读取的最少附件。

不要机械复制完整会话、整个仓库、无关历史或大段重复材料。信息不足会影响核心判断
时，先收集可在本地确认的事实；仍缺少用户决定时集中询问一次。

代码和仓库任务按相关性记录：

- 仓库与工作目录；
- 当前 branch 和 commit SHA；
- 工作区是否 dirty；
- 与问题直接相关的 diff；
- 已运行的关键测试、命令和结果；
- 每个附件被选择的原因。

本地路径只用于 Codex 定位材料，不能替代给网页端的上下文。目标模型不能访问某个
本地文件或目录时，必须在以下方式中选择一种：

- 作为已索引附件上传；
- 把决定结论的内容、结构、diff 或验证结果提取进实际提交文本；
- 只把文件名、仓库、branch 和 SHA 作为证据身份，同时提供必要事实摘要。

不要在直接输入或 handoff 中仅写“请读取 `/Users/...`”或“详见本地仓库”。

## 2. 准备合适的提交材料

先选择能完整承接上下文的最轻载体：

- 一条输入能清楚包含必要事实、用户已锁定约束、当前推断、暂定方案、分歧、未知项和
  输出要求时，直接把完整文本输入 ChatGPT，不创建 handoff 文件。
- 信息较长或需要稳定结构、较多附件索引、跨轮复用，或用户明确要求 handoff 时，才生成
  “任务主题-handoff.txt”；简单、一次性且用户明确要文件时可使用 `handoff.txt`。
- 是否需要附件与是否生成 handoff 分开判断。直接文本可以索引页面附件；没有实际附件
  时不运行附件能力预检。

生成 handoff 时，已有 case 或 artifacts 目录就放入对应运行材料目录；没有合适位置时
使用安全的临时目录，并至少保留到结果回收和本地核验完成。

无论使用直接文本还是 handoff，都保留事实、推断、偏好和未知项的边界；标题按需要取舍：

```text
任务目标
预期交付
已确认事实
用户已锁定的约束与决定
当前推断
待审方案或实现（暂定）
非目标
判断标准
关键证据与材料闭合表
已知分歧
未知项
希望重点判断的问题
输出要求
```

让实际提交文本满足以下质量：

- 信息足够支撑独立判断，不用追溯完整 Codex 会话；
- 先给证据和判断标准，把待审方案与它们分开，允许目标模型独立得出结论；
- 只有用户明确锁定的决定才标为不重开；不把“唯一待决项”或“不应重新讨论”
  写成默认审阅边界；
- 附件逐个说明用途、来源和可信边界；
- 代码结论绑定到真实 branch、SHA、dirty 状态、相关 diff 和验证结果；
- 网页端无法访问的本地路径已经转成附件、必要摘录或结构化证据；
- 不为追求短而删除会影响结论的条件；
- 不把推断、用户偏好或未经验证内容写成事实。

### 冻结上传集合

本轮有附件时，在进入 Browser 前按 [IAB 人工上传与排障](references/iab-manual-upload.md)
形成唯一、可核对的冻结集合。记录文件名、用途、源路径、发送副本路径和 SHA-256；
附件跨目录或同名时，生成一个临时发送目录保存冻结副本。上传后任一源文件或发送
副本变化，都把页面附件标为已失效，停止发送并重新冻结、上传。

使用直接文本时，ChatGPT 输入框承载完整、自包含的上下文；有附件时直接写入页面实际
文件名及其用途。使用 handoff 时，它作为主上下文，输入框只写简短控制语，例如：

```text
请完整阅读 <页面实际 handoff 文件名> 和已索引附件，基于其中的事实、约束与判断标准独立完成任务。
可以反对当前方案；请明确区分事实、推断、建议和待验证项。
```

角色、视角和输出格式写入本轮实际提交文本，不建立固定的
review / plan / implement 路由表。

### 图片产物

目标清楚的简单生图直接使用精炼提示词，不为形式完整强制创建 handoff。保留真正
决定结果的信息，例如用途、主体、构图、风格、比例以及必须保留或避免的内容；背景
复杂、需要参考图片或后续复用时，再整理 handoff 或任务已有的 brief。

参考图片按最少附件和外发风险规则处理。图片生成仍使用用户指定、页面实际可用的
档位，不硬编码专用模型，也不把普通生图请求自动升级到 Pro。

### 同一任务续评

已经取得上一轮结果，又要携带新增证据复审时，默认复用原网页对话。新增信息能由一条
文本完整承接时直接输入；只有信息较长、包含新附件或需要复用时才生成
`handoff-followup.txt`。它不复制完整首轮 handoff，而是建立足够明确的证据桥：

```text
原始问题与当前目标
上一轮结论及关键依据
上一轮之后新增的用户决定
新增本地事实、实验或实现结果
哪些旧假设已被证实、限定或推翻
当前仍有分歧的决策点
希望重新判断的问题
要求说明维持、修订或反转结论的理由
第一版必须做、只保留规则、以后触发再做的边界
```

续评材料必须自包含到足以理解新增证据，不能只写“请结合之前内容重新看”。同时利用
原会话保留上一轮论证，不把所有历史再次上传。独立新问题或用户明确要求 clean-room
时才新建对话。

使用 followup 文件时，控制语应直接说明新证据和重审要求，例如：

```text
请结合原会话和 handoff-followup.txt 中的新增证据重新判断。不要以维持上一轮结论为
目标；请说明这些证据是否足以让你维持、修订或反转观点，并给出理由与最小落地边界。
```

## 3. 选择最少附件并检查外发风险

只附加用户明确选择或本轮实际提交文本明确索引、且与任务直接相关的文件。

- 逐个核对文件名、数量和选择理由。
- 材料闭合表为每个来源标记“已上传 / 已摘录 / 仅作身份引用”；仅作身份引用时，
  直接输入或 handoff 必须已提供支撑判断所需的事实摘要。
- 附件清单、冻结集合与页面附件必须一一闭合；网页端不能访问的本地链接不能独立
  承担证据。
- PDF、DOCX、PPT 中的重要图表、流程图或设计图应单独作为图片附件；不要假设内嵌
  视觉信息会被完整读取。
- 上传能力判断、人工检查点和上传异常按已加载的 IAB 参考文件处理。

首轮外发默认只保留直接改变结论的最小证据。原始项目拓扑、客户识别信息、无关告警和
全量日志先摘要或脱敏；只有它们对当前判断不可替代且用户已授权外发时才作为附件。

提交前直接阻止凭据、Token、私钥、Cookie、session dump、数据库备份、生产用户
数据、患者隐私或明显客户敏感材料。公司源码、业务日志、个人数据等能否进入当前
ChatGPT 账号取决于组织政策和用户外发授权；存在实质不确定性时停止确认。

不要读取、检查或持久化账号凭据、Cookie、Browser Profile 或认证存储。需要登录、
切换账号或确认身份时交给用户。

## 4. 通过提交前质量门

在任何 Browser 发送动作前重新检查：

- 目标、预期产物、判断标准和关键问题是否明确；
- 必要事实、证据、约束、分歧和未知项是否齐全；
- 本轮存在文件材料时，handoff（如有）、源文件和冻结发送副本的 SHA-256 是否仍与上传前记录一致；
- 网页端不可达的本地路径是否已经转换为真实附件或可消费证据；
- 附件是否最少、已索引、无确定性高风险材料；
- 本次对话应新建还是复用；
- 复用对话时是否确认页面里存在上一轮问题和回复；
- 用户是否已经授权本次发送；
- 当前 Browser 是否连接到唯一、状态明确的 ChatGPT 页面；
- 当前网页账号是否符合用户预期；
- 页面的产品档位、模型选项、思考强度和当前选中状态是否已分开核对，并与用户要求完全一致；
- 页面显示的附件名和数量是否与实际提交文本中的索引一致；
- 同一请求是否已经在目标对话中提交。

对话选择规则：

- 独立任务默认新建普通 ChatGPT 网页对话，减少旧上下文污染。
- 同一任务的续评、追问或补充材料默认复用原网页对话。
- 续评默认只提交新增证据桥，不重复上传完整旧材料；旧材料已经失效时明确标记替代关系。
- 无法可靠判断是否同一任务时，给出一句建议并让用户决定。
- 每次追问都是新的发送，需要新的授权。
- Temporary Chat 只在用户明确需要 clean-room、理解 Memory 和恢复差异后使用。

模型选择规则：

- 只使用用户指定、提交时页面实际可选的模型或推理预设。
- 用户未指定时可以给一句成本与质量建议，但不能静默决定高成本档位。
- 产品档位、模型名称和思考强度是不同页面状态；不把“尚未选中”、“相关控件未展开”
  或“页面正在变化”判为目标不可用。
- 目标首次未出现时，只对相关控件等页面稳定后再做一次有界复查；仍不可确认时停止，
  展示实际选项，不选择近似档位。
- 不维护固定模型枚举，也不假设模型和推理强度可以任意组合。
- 页面显示 `Pro` 等产品档位时按页面原文记录，不根据标签猜测底层 GPT 版本。

展示紧凑摘要：

```text
目标：<一句话>
模型：<页面实际选项>
对话：<新建或复用>
材料：<直接提示词 / 任务 handoff / handoff-followup.txt> + <N> 个附件
风险：<无明显风险 / 需用户确认>
动作：<仅准备 / 等待确认 / 等待人工上传 / 将提交并等待 / 将只提交>
```

只准备时在这里停止。已有清晰发送授权且质量门通过时，不重复索要形式化确认。
有附件时，原发送授权仍然有效；人工上传完成后只需核对页面附件，不重新询问是否
发送。页面动作在执行时要求确认的，遵循当前产品的 action-time confirmation。

## 5. 通过内置 Browser 和受支持的附件路径只提交一次

实际操作 Browser 前，加载当前会话提供的 `browser:control-in-app-browser` Skill，
完整遵循它的页面观察、唯一定位、动作确认、标签页生命周期和状态核对规则。该 Skill
不可用时 fail closed。附件路径以已加载的 IAB 参考文件为准。

页面观察只读取当前决定所需的控件和可见状态，优先屏幕截图和目标控件局部读取。
不一次性抓取完整 DOM、全部按钮文本或无关页面状态。局部读取超时或运行内核重置时，
重新连接后先只读恢复原对话、附件和发送状态，不因观察失败重发。

调度期间优先保持 Browser 侧栏可见，方便用户观察过程和必要时介入。侧栏显隐只影响
可观察性，不作为执行或成功判据；如果当前产品无法控制侧栏显隐，但同一个 in-app
Browser 标签页仍可正常操作，则继续使用原有 Browser 链路，不因此阻断调度。

Browser 是第一版页面主链适配器，按顺序完成：

1. 打开或接管用户可见的普通 `chatgpt.com` 页面。
2. 按对话选择规则新建或复用普通网页对话；续评时先确认上一轮上下文确实存在。
3. 观察并核对当前网页账号；需要登录或切换时交给用户。
4. 分开读取产品档位、模型选项、思考强度和当前选中状态，精确匹配用户要求。
5. 无附件时继续下一步；有附件时按 IAB 参考文件完成冻结、上传或人工检查点，
   再从页面核对所在对话、附件数量和身份。
6. 人工路径中若用户已经误触发送，转为核对现有提交，绝不重复发送。
7. 输入完整直接文本、简短控制语或图片生成提示词。
8. 再次检查同一请求尚未发送、目标档位和附件仍正确。
9. 只执行一次发送动作，并确认页面已经接受该次提交。

Browser 只操作普通 ChatGPT 网页，不调用 API、MCP、代理、私有接口或其他账号。
页面是否已发送不明确时先只读检查同一对话，绝不再次发送。

## 6. 在同一网页对话中无干预等待

发送是本流程唯一不可重复的提交点。用户明确要求“只发送、不等结果”时，页面确认
已接受请求后立即返回目标档位、会话引用、材料和“已提交、结果未回收”状态；不进入等待、
结果读取或恢复链。发送状态不清时仍只读核对原对话，绝不为尽快返回而重发。

其他请求在发送后保持同一 ChatGPT 网页对话，Browser 只进行不会改变本轮状态的
等待和只读观察：

- 不点击“立即回答”；
- 不点击“停止回答”；
- 不因本地超时再次发送；
- 不复制请求并新开替代对话；
- 不静默切换模型或推理档位；
- 不因完成状态不清重试；
- 不在没有新授权时追问。

十几分钟或更长的推理可能是正常路径。长时间没有最终结果时，报告仍在等待并继续
观察同一网页对话。用户要求取消时，先说明可能损失当前推理，再按新的明确授权处理。

## 7. 从同一网页对话取得结果

文本回复完成后，Browser 从本轮一直保持的同一网页对话读取完整结果并带回 Codex。
正常路径不调用 `list_threads` 重新匹配候选，也不把 DOM 读取交给用户。

读取时核对：

- 最终回复属于本轮已发送请求；
- 回复已经完整结束，不把中间状态当作最终结果；
- 必要的代码块、表格、引用和结论已完整取得；
- 原网页对话仍被保留，便于异常恢复。

图片生成完成后，Browser 定位本轮同一张图片，使用当前页面和 Browser 实际支持的
保存、下载或媒体提取方式取得文件，并确认本地文件可以定位。标准 download 事件
没有出现时，结合页面完成状态和本地文件存在性判断；需要恢复时继续处理同一张图片，
不重新生成替代产物。

## 8. 只在 Browser 失败后恢复结果

只有 Browser 控制断开、页面不可恢复或结果读取不完整时，才进入原生 thread
恢复：

1. 使用当前可用的 ChatGPT 对话列表能力定位同一对话。
2. 使用读取能力取得完整回复。
3. 候选不唯一时停止确认，不按标题、时间或内部 ID 猜测。
4. 原生恢复仍失败时保留原网页对话和产品入口，由用户可见地复制或保存结果。

不要依赖固定 backing kind、thread ID 与网页 chat ID 映射，或所有网页对话都可见。
`send_message_to_thread` 不用于第一版提交或追问，因为它不能核对或覆盖 ChatGPT
页面实际档位。任何恢复失败都不得触发重新发送。

图片文件未能取得时优先回到原网页对话恢复同一产物；thread 中的文字记录不能替代
本地图片文件。

## 9. 完成本地核验

外部回答只提供高质量判断或候选产物，Codex 保留最终核验责任：

- 对照原始提交文本和附件检查目标、约束和关键问题是否覆盖；
- 回到仓库核对文件、Git 状态和实现事实；
- 对代码、命令或配置运行适度测试；
- 区分回答中的事实、推断、建议和待验证项；
- 续评时比较前后结论，记录模型维持、修订或反转观点的依据；
- 明确采纳、部分采纳、拒绝和待验证内容；
- 图片产物检查文件格式、尺寸和实际画面是否满足本次要求；
- 只在当前任务已有相应修改授权时继续实施。

交付时至少说明：

```text
目标档位：<页面实际选项>
对话：<可用的原网页对话引用>
材料：<handoff 绝对路径 / 直接提示词>
产物：<文本结果摘要 / 图片本地路径>
回收方式：<未回收 / Browser 同页读取 / 原生异常恢复 / 用户可见恢复>
调度状态：<自动调度成功 / 人工辅助调度成功 / 已提交、结果未回收 / 降级恢复 / 未提交>
核验结论：<已通过 / 部分通过 / 未通过>
采用情况：<采纳、部分采纳、拒绝、待验证>
结论变化：<首次审查 / 维持 / 修订 / 反转，以及主要依据>
归档状态：<未要求 / 已完整归档 / 归档未完成>
```

默认不创建 response、validation、manifest、数据库或状态文件。只有任务价值和后续
复用明确需要时，才在已有 case / artifacts 中保存额外结果。

## 10. 按明确要求完整归档

用户明确说“完整留存”“归档这次对话”，或当前任务已授权保存这类产物时，在释放页面
控制前生成一份可独立阅读的耐久 Markdown 记录，保存到已有 case / artifacts 目录。默认只生成
这一份记录，不建数据库或运行状态系统。

记录包含：

- 页面实际显示的产品档位、模型或思考强度，以及不可得字段的明确说明；
- 会话 URL、标题、提交时间和页面显示的思考时长；
- 实际提交的直接文本或控制语、handoff（如有）和附件身份、SHA-256 与完整性说明；
- 本轮完整可见回复正文；不声称保存隐藏推理或页面未显示内容；
- 本地事实复核、采纳、部分采纳、拒绝和待验证项；
- 外发范围、脱敏处理和敏感性说明。

稳定源文件保留链接和 SHA-256，不重复复制。只有实际发送材料位于可能消失的临时目录时，
才把该冻结副本复制到归档目录。原网页对话继续保留为可恢复来源，本地记录不替代它。

## 11. 技术方案审查的证据闭环

外部模型的第一轮结论与当前方案冲突时，先判断分歧属于哪一类：

- 用户目标或可接受代价：停止并由用户决定；
- 本地源码、构建、运行时或部署事实：回到本地核验；
- 可通过小规模对照验证的工程假设：在当前授权内设计受控 Spike；需要新增写入或扩大
  实验范围时先获得授权；
- 纯设计判断：列出双方依赖的假设和重新评估条件。

只有新增信息可能改变判断时，才建议再次使用高成本档位。第二轮续评应提供控制变量、
代表样本、关键实现、自动检查、真实路径观测、工程成本和剩余未知项，并明确要求目标
模型说明新证据是否足以改变观点。

不要用多个模型投票替代事实，也不要在没有新增证据时连续追问。选型结论收敛后，再
单独要求区分：第一版必须建设、当前只需规则约束、真实信号出现后再建设。Codex 最终
把外部意见与本地证据合并为采纳、调整、拒绝和待验证清单。

## 失败处理

| 场景 | 处理 |
| --- | --- |
| Browser 或 Browser Skill 不可用 | 停止在提交前，不切换执行链 |
| ChatGPT 网页未登录或账号不符 | 停止，交给用户登录、切换或确认 |
| 目标首次未出现 | 等页面稳定后对相关控件有界复查一次；仍不可确认才停止 |
| 附件能力、上传或标签页异常 | 按 IAB 参考文件处理，停止试错且不重发 |
| 冻结后源文件或发送副本变化 | 把页面附件标为失效，重新冻结、上传和核对 |
| 页面局部读取超时或运行内核重置 | 重连后只读恢复原对话、附件和发送状态，不重发 |
| 页面目标、附件或发送状态不唯一 | 停止确认，不猜测、不再次发送 |
| 只发送模式已确认页面接受 | 返回会话引用和“已提交、结果未回收”，不等待 |
| 页面已发送但仍在推理 | 同页被动等待，不干预 |
| Browser 控制断开或读取不完整 | 恢复同一页面，失败后才尝试原生 thread 读取 |
| 原生恢复候选不唯一 | 停止确认，保留原对话和产品入口 |
| 输出质量不足 | 先本地分析；追问或重开需要新授权 |
| 图片已生成但本地文件不可定位 | 恢复同一张图片的保存或提取，不重新生成 |
| 续评材料只有本地路径或“同上” | 停止提交，转换为附件、必要摘录和新增证据桥 |
