# codex-chatgpt-dispatch

> 特定环境 Skill：面向 ChatGPT 桌面应用中的 Codex + 内置 Browser。

## 是什么

`codex-chatgpt-dispatch` 帮助 Codex 把当前任务所需上下文整理完整，通过内置
Browser 操作普通 ChatGPT 网页对话，交给用户指定的模型或推理预设，只提交一次、
然后按用户要求立即返回，或在同一页面等待、回收并核验文本或图片结果。一条输入足以
完整承接上下文时直接输入；只有信息结构、较多附件索引、复用需要或用户明确要求时才生成
任务化 handoff。附件任务会先
冻结最小发送集并核对官方 Browser 能力边界；需要人工上传时，Skill 会提供集中的发送目录、
可点击文件链接和完整性信息，再由 Browser 核对页面附件。
对于同一任务的续评，它会复用原网页对话，用新增证据桥要求目标模型明确维持、修订
或反转上一轮判断。

它处理调度协议和上下文质量，不管理账号，不提供模型网关，也不建设任务队列或自动
重试系统。

## 何时用

必须显式调用，例如：

```text
$codex-chatgpt-dispatch 先整理当前方案的 handoff，不要提交
$codex-chatgpt-dispatch 用页面当前可用的 Pro 深度评审并提交一次
调用 codex-chatgpt-dispatch，组织发送就行，不用等结果
调用 codex-chatgpt-dispatch，把这个实现交给指定模型独立判断
$codex-chatgpt-dispatch 用页面当前非 Pro 档位生成一张配图，保存后在本地检查
$codex-chatgpt-dispatch 完整留存这次对话
```

普通评审、模型讨论、材料整理或“要不要让 Pro 再看一遍”不会触发该 Skill。

## 工作流程

```text
显式触发
→ 盘点必要上下文
→ 优先使用能完整承接上下文的直接文本，必要时才生成任务 handoff
→ 独立判断是否需要附件，并选择最小附件集
→ 核对账号、目标档位、材料和发送授权
→ 有附件时静默核对官方能力边界与本机版本
→ 冻结附件和 SHA-256；必要时输出集中发送目录并保留侧栏标签页
→ Browser 核对页面附件，在普通 ChatGPT 网页只提交一次
→ 只发送模式立即返回；其他模式在同页无干预等待并取得结果
→ Browser 失败时才用原生 ChatGPT thread 恢复
→ Codex 本地核验
→ 用户明确要求时完整归档可见对话和采纳结论
→ 有新增证据时复用原会话续评，而不是重新复制完整上下文
```

Browser 是第一版页面主链适配器。当前有附件时，人工上传是正常的受限协作检查点，
其余页面动作仍由 Browser 完成，状态记录为“人工辅助调度成功”；意外接管其他核心
步骤才算降级恢复。原生 ChatGPT thread 能力只用于 Browser 控制断开、页面不可恢复
或结果读取不完整的异常场景。

静默预检只在下一次实际附件调度开始时运行，不做后台轮询。普通版本更新不会打扰
用户；只有官方明确恢复支持、出现可靠能力标志或官方资料实质冲突时，才提示恢复信号
并请求一次无敏感测试文件探测授权。版本变化本身不作为恢复证据。

## 前置条件

- ChatGPT 桌面应用中的 Codex 可以使用；
- 当前会话提供内置 Browser 和 `browser:control-in-app-browser` Skill；
- Browser 可以打开或接管普通 `chatgpt.com` 页面；
- 用户可以在 Browser 保留的同一侧栏标签页中完成一次人工附件上传；
- 当前 ChatGPT 网页账号已登录，且用户有权外发选定材料；
- 提交时页面实际提供用户指定的模型或推理预设；
- Browser 能保持或恢复同一网页对话并读取最终结果。

在 Codex CLI、IDE、纯终端或缺少内置 Browser 的表面可以准备直接文本或 handoff，但第一版
不会完成自动提交。Browser 不可用时 fail closed。

## 核心边界

- 显式触发与发送授权分开。
- 一条文本足够承接上下文时直接输入，不因任务复杂而强制创建 handoff 文件。
- 是否生成 handoff 与是否需要附件分开判断；只有实际需要附件时才运行上传能力预检。
- Browser 操作前加载并遵循 `browser:control-in-app-browser`。
- 调度期间优先保持 Browser 侧栏可见；侧栏显隐不可控但同一 in-app Browser 标签页
  仍可操作时，不阻断任务。
- 附件任务先只读核对当前官方边界与本机版本；官方仍不支持、资料不清或只有版本变化
  时，不尝试 `filechooser` / `setFiles` 自动上传。
- 发现明确恢复信号时只请求一次安全探测授权；授权前保持人工路径，探测不使用真实
  材料、不发送消息，失败后不连续重试。
- 进入人工路径时一次给全文件名、用途、发送目录、绝对路径和可点击链接，暂停前使用
  `tab.markHandoff()` 保留标签页。
- 附件跨目录或同名时生成临时单一发送目录，使用可点击链接和 SHA-256 冻结实际发送版本。
- 用户上传后由 Browser 从页面核对附件名和数量；已有发送授权不为形式完整重复确认。
- 页面自动添加 `(N)` 先按展示重命名处理；只有冻结集合仍无法唯一对应时才停止。
- 上传后源文件或发送副本变化会使页面附件失效，必须重新冻结与上传。
- 人工上传不记为自动调度成功，使用“人工辅助调度成功”保持完成边界诚实。
- 使用用户指定、提交时页面实际可用的模型或推理预设。
- 分开核对产品档位、模型、思考强度和当前选中状态；有界复查后才能判定目标不可用。
- 发送前核对网页账号、目标档位、附件名和数量。
- 同一请求没有新授权时最多发送一次。
- 用户要求只发送时，确认页面接受后返回“已提交、结果未回收”，不等待。
- 同一任务续评复用原网页对话，但每次续评仍需要新的发送授权。
- 本地路径不能作为网页端上下文；必须转换为附件、必要摘录或结构化证据。
- 页面显示 `Pro` 等产品档位时按原文记录，不猜测底层具体模型版本。
- 永远不点击“立即回答”或“停止回答”。
- 长等待不触发停止、重试、重开或降级。
- Browser 在同一网页对话中等待并读取结果。
- 原生 thread 只负责异常恢复，`send_message_to_thread` 不承担提交或追问。
- 用户手工接管不计为自动调度验收通过。
- 外部回答必须回到本地证据核验。
- 用户明确要求完整留存时，只生成一份包含可见对话、附件身份和采纳结论的耐久 Markdown 记录。
- 图片结果需要定位本地文件并检查格式、尺寸和实际画面；保存异常时恢复同一产物。
- 技术方案存在分歧时，优先把可验证假设转成受控 Spike；有新增证据后再续评。
- 续评记录模型维持、修订或反转结论的理由，并区分立即建设与未来触发项。
- Pro 等高成本档位不作为常规 eval。

## 数据与账号

Skill 不读取或持久化 Cookie、Browser Profile、登录凭据和认证存储。凭据、Token、
私钥、session dump、数据库备份、生产用户数据、患者隐私和明显客户敏感材料会在
提交前阻止。

公司源码、业务日志或个人数据能否进入当前 ChatGPT 账号，取决于组织政策、当前
账号设置和用户外发授权。Skill 不自动修改 Memory、训练数据控制或文件 Library
设置。
